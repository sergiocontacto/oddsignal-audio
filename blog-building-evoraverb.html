Building EvoraVerb: notes from the first release

EvoraVerb is the first thing ODDSIGNAL AUDIO has released. Most of what went wrong had nothing to do with audio.

It was called LushVerb

The project started under a different name and kept it through the whole first phase of development. Renaming it to EvoraVerb late meant chasing the old name through build scripts, artifact paths and bundle identifiers — and a run of failed builds that were all the same mistake in different files.

The internal CMake target is still called LushVerb today. It has no effect on anything the user sees, and renaming it now would break more than it would tidy.

Building for macOS without a Mac

We develop on Windows. macOS plugins can only be compiled on macOS, which normally means buying a Mac before you can ship to half your potential users.

Instead the macOS builds run on GitHub Actions, on their hosted macOS runners. Push to the main branch, and a VST3 and an Audio Unit come out the other end. It works well, and it took a dozen failed runs to get there: deprecated action versions, JUCE accidentally tracked in git instead of cloned, Xcode putting artifacts in different paths than expected, and the file names that changed with the rename.

JUCE is now pinned to version 9.0.1 in the workflow. Cloning whatever is on master means the macOS binary can be built from a different framework version than the Windows one, and a build can break overnight without a single commit.

The ZIP that broke every install

GitHub Actions hands you build artifacts as ZIP files. ZIP does not store Unix permissions.

So the plugin arrived on the tester's Mac without its executable bit. macOS refuses to load it, the DAW shows nothing, and no error anywhere explains why. The fix is to tar the bundles before uploading them, because tar does preserve permissions, and to hand out the tarball rather than the ZIP.

A whole class of "it does not work on my machine" reports come from this. The plugin is fine; the delivery format quietly stripped something it needed.

A universal binary that was not

The worst one was invisible until we went looking.

The CMake configuration never set a deployment target or a list of architectures. Without them, a build inherits whatever machine compiled it. The GitHub runner is Apple Silicon on a current macOS, so the binaries came out arm64 only, requiring macOS 26.5.

That combination excludes every Intel Mac and every Mac more than a few months behind on updates. The build succeeded, the plugin ran perfectly on a modern Mac, and almost nobody else could load it. Worse, it fails the same silent way as the permissions bug: the plugin simply does not appear.

Two lines, placed before project() so CMake actually reads them, fixed it:

  • CMAKE_OSX_DEPLOYMENT_TARGET set to 11.0
  • CMAKE_OSX_ARCHITECTURES set to arm64;x86_64

The lesson we took from it is that a green build is not a working build. We now read the Mach-O headers of every macOS release before it goes out and check the architectures and minimum version by hand.

Where it is going

Version 1.1 is what you can download today. In progress is 1.2, adding typed value entry and user presets — both from beta feedback, both things that only become obvious once other people use what you made.

Apple Developer signing and notarisation are the next thing on the list, so that Gatekeeper stops asking. AAX is further out; it needs Avid's SDK and a PACE signature.
